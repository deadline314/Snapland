# 原生驗收的時鐘與等待期限

## 2026-10-24 查證

本輪十二款遊戲驗收在未鎖定模擬步長的軟體渲染中，噴泉、人潮與大合奏的實際輸入偏離預期時點。原始失敗結果保留；不修改遊戲的計分、命中窗口或成就資格。

改用固定步長後，又發現彩帶與合奏的驗收誤用即時模式等待期限。實際最小探針在 Godot 4.7.2 傳入 `--headless --fixed-fps 60 --script …`，`OS.get_cmdline_args()` 只留下腳本參數。[Godot OS 文件](https://docs.godotengine.org/en/stable/classes/class_os.html#class-os-method-get-cmdline-args)明確指出已由引擎處理的選項不在回傳清單；自訂參數應置於 `--` 後並由 `get_cmdline_user_args()` 讀取。[命令列文件](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)也區分引擎選項、自訂選項與 Movie Maker 的固定步長。兩頁本輪實際閱讀，不把文件文字當成遊戲驗收。

## 執行約定

彩帶與合奏在固定步長驗收時，驅動器同時提供引擎的 `--fixed-fps 60` 與使用者參數 `-- --review-fixed-clock`。Movie Maker 可從實際輸出路徑辨識。固定模式只選擇既有、有上限的等待保護；不設定模型時間、不輸入結果、不放寬評分，也不把軟體渲染速度當成玩家硬體的 FPS。

四分之一速度時，相同數量的引擎影格只前進四分之一的遊戲時間。從遊戲秒數換算的影格等待上限也須除以實際時間倍率，不能只延長牆鐘上限，否則三拍預備尚未結束就會被誤判卡住。彩帶仍保留原來的最大影格數及外層有限程序期限；所有窗口與分數維持原值。

每組保存實際命令、模式、隔離存檔、原始失敗與最終結果。先查明是輸入、實際遊戲、繪製或驗收驅動器造成問題；一個階段的通過訊息不能覆蓋後續失敗的程序結果。Dummy 音訊與可播放檔案均不能當作實際試聽。

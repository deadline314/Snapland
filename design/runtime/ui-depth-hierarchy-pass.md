# ART-20 wardrobe/shop paper hierarchy pass

## Scope and design

This is a bounded candidate refinement of the existing fitting-room surface. It changes only the shared paper style helpers and the wardrobe panel, without changing `Progress`, wardrobe definitions, the character atlas, main routing, or purchase/equip callbacks.

The fitting-room view remains a quiet harbor paper counter: the left portrait sits inside one visibly recessed mirror frame with a thicker right and lower paper edge and one cast shadow. The right column stays functional and uses a small coin ledger, three page tabs, the current item list, a status line, then the action row. The selected page is a deep-teal active tab with brass edge and high-contrast light text; idle pages stay lower and quieter. Only the next committed action receives dark teal fill and a brass paper edge: apply, wear, or purchase. Cancel and alternate actions stay pale paper. This avoids equal-weight buttons and avoids adding decorative stamps or extra ornament.

Selection remains a draft. Choosing an appearance or clothing item previews it without saving or spending. Item rows keep the actual catalog price or ownership/equipped state. If the selected shop item is unaffordable or already owned, purchase is disabled and the status line states the required price or next available action; no price is substituted or hidden. Price labels and insufficient-funds status use dark coral ink with at least 4.5:1 contrast against the paper surface. Existing Enter focus restoration, direction preview, free appearance controls, purchase, equip, cancel, and small-window menu adaptation remain intact. At compact scale, the open panel recalculates its fitting-mirror height and module gaps when the window changes size; it restores the full-height composition when resized back. The centered avatar remains aspect-fitted. No animation is introduced; reduced-motion keeps the same static depth and geometry.

## Source directions used

The sources below were read in the existing `ui-quality-survey.md` and `ui-depth-survey.md`. This pass reuses those textual readings; it does not claim new source-image inspection or gameplay viewing.

| Source and read scope | Applied here | Explicitly not copied |
|---|---|---|
| Apple HIG, [Materials](https://developer.apple.com/design/human-interface-guidelines/materials): foreground/background separation and text contrast | Separate the character viewing well, list, status, and actions by material role; keep label surfaces opaque. | No translucent glass or blur over labels. |
| Microsoft Fluent 2, [Elevation](https://fluent2.microsoft.design/elevation/): fixed light direction, key/ambient shadow relationship | One consistent lower-right cast shadow communicates the raised fitting frame. | No independent shadow stacks or moving light. |
| Microsoft Windows Apps, [Layering and elevation](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/layering): elevation explains navigation and importance; too many layers create noise | Reserve the strongest surface treatment for the active page and one committed action. | No card-by-card elevation ladder. |
| Google Android Developers, [Add shadows in Compose](https://developer.android.com/develop/ui/compose/graphics/draw/shadows): default elevation versus drop shadow and inset shadow | Use a single cached-on-control stylebox treatment instead of accumulating multiple drawn shadows. | No inset shadow or animated drop shadow. |
| Godot Engine, [StyleBoxFlat](https://docs.godotengine.org/en/latest/classes/class_styleboxflat.html): shadow, borders, margins, and hit-rect distinction | Express thickness with border widths and a bounded shadow; preserve the existing Control bounds and margins. | No expand margins that enlarge perceived or actual click targets. |
| Nintendo, [Super Paper Mario interview](https://www.nintendo.com/en-gb/News/2007/Interview-Super-Paper-Mario-249673.html): paper as a legible interface language tied to game function | Give the active page a distinct fitted-tab role with a dark teal face and brass edge. | No folded character shapes, copied icons, or 2D/3D transformations. |
| Nintendo, [Super Paper Mario Wii manual](https://csassets.nintendo.com/noaext/image/private/t_KA_PDF/Wii_Super_Paper_Mario?_a=DATAg1AAZAA0), pp. 2–3: explicit menu categories and status terms | Keep page names, current selection, currency, price, and ownership written out. | No borrowed menu composition or game-specific terms. |
| Housemarque, [Returnal UX article](https://blog.playstation.com/2021/05/11/unpacking-returnals-ux-design-gameplay-first-ui-retro-futuristic-tech-and-accessibility/): primary information close to the interaction, secondary material at the edge | Place item price beside the selected item and the purchase result in the action/status region. | No extra always-visible HUD or explanatory text wall. |

## Verification

The local UI test checks the active tab face and text contrast, measured preview frame edge/shadow, primary-versus-secondary action surfaces, price and deficit readout contrast, direction preview, unsaved appearance draft, keyboard focus and list scrolling, purchase/equip behavior, reversible standard/compact profiles, and 800×600 modal/HUD bounds. The static preview frame is also checked after enabling reduced motion. Godot 4.7.2 candidate import succeeded. The wardrobe UI scene passed 60 PASS lines with zero ERRORs across the standard and 800×600 layouts. These are headless hierarchy and interaction checks, not native visual acceptance.

## Bounded native before/after fixture

`game/tests/native_wardrobe_hierarchy_review.tscn` reuses the committed native review's real key and pointer-event path and its Main screenshot writer. It starts with zero isolated coins, opens the wardrobe with C, clicks the appearance/closet/shop tabs, and selects the catalog's exact 100-coin gold outfit with the pointer. Both variants require the selection, keyboard focus, and captures to work; candidate runs additionally require the disabled purchase state and exact required-price status. Baseline runs print the actual price/status/disabled state and compact modal/control bounds as diagnostics, then report `BASELINE_CAPTURED` rather than passing the new hierarchy criteria. The fixture captures the same shop in reduced-motion mode and at physical 800×600, and does not invoke `pressed` signals or purchase anything. A 120-second watchdog bounds the run.

To compare baseline and candidate, the same bounded fixture was run in a clean HEAD baseline and this candidate with isolated save paths and actual key/pointer events. It captured six matching views in each variant: standard appearance, closet, unaffordable 100-coin shop selection, reduced-motion shop, and appearance/shop at physical 800×600. The baseline reports diagnostic bounds and price state; those captures are comparison evidence, not acceptance of the new compact fit or price treatment. Candidate v4 completed all six captures with no script or engine errors. Root manually reviewed the standard shop, reduced-motion contrast, and both compact captures: the selected gold item remains visible after resizing, the full avatar and action row fit, and selected price/status text stays readable. The compact window is 800×600 physical pixels; Godot's captured content image is 800×450. This is an automated native UI comparison with targeted visual review, not a human playthrough or a complete visual review of every ART-20 screen.

The standard-only MovieMaker recording completed at 242 frames, 60 fps, 1280×720, with no engine or script errors. Playback reached the end at 4.033 seconds; Root reviewed its start and end frames and accepted this bounded four-page wardrobe UI review. This does not claim a human purchase/playthrough or full wardrobe animation review, and it does not complete ART-20's wider interface scope.

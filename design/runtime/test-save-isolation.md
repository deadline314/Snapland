# Test-save isolation

The `Progress` autoload inspects command-line scene/script paths before connecting save-on-change or loading progress. Test and `.review` launches require `SNAPLAND_SAVE_PATH` to name an absolute filesystem save path outside Godot's default userdata directory. Godot virtual paths (`user://`, `res://`, and other `://` schemes), missing paths, relative paths, and paths under default userdata are rejected before load, migration, or write; startup exits with code 1. Normal game launches continue to use the existing `user://progress.json` fallback.

The focused guard test builds a minimal child project under a unique directory beside the externally supplied isolated save (the Python runner supplies an operating-system temporary directory) and gives it a unique application name. Before seeding anything, it verifies that the matching default profile under the platform-specific Godot userdata parent (derived from the running engine, not Windows-only environment variables) did not already exist and that a probe child reports exactly that path. Rejected-path child launches use only this verified fake profile; the harness seeds `progress.json`, `.bak`, and `.tmp`, then checks their SHA-256 hashes after every child. The `NEGATIVE_FAKE_PROFILE_HASHES_UNCHANGED` result is emitted after these rejection checks and before either positive round trip. It removes only those exact fixture files and the exact Godot log files created under the unique fixture profile.

The explicit-path positive child writes and reloads through a separate save path under the temporary fixture root. Cleanup removes that test-owned save file and its known `.bak`/`.tmp` sidecars individually, since a successful save may leave a backup behind. The test then seeds the fake default `user://progress.json` with a known payload and launches a root-level `normal_save_roundtrip.gd` fixture entrypoint. That path is intentionally outside `game/tests/` and `.review/`; the child verifies it is classified as an ordinary launch, runs with an empty `SNAPLAND_SAVE_PATH`, checks the loaded coins/intro/time-phase values, changes coins, and calls the normal `Progress.save_progress()` path. A fresh ordinary child process reopens the same fake default profile and verifies the new value. The harness prints each ordinary child's captured stdout/stderr with its mode and exit code, and both processes must report the exact verified fake application userdata directory. Cleanup is restricted to the fixture's known files and verified, uniquely named profile. No child receives or opens the calling Snapland project's live userdata path.

The Windows regression replays the native scene without `TEMP` and `TMP`; Linux CI additionally has no Windows `APPDATA`. The fake profile must still be probed exactly before any seed or deletion, and the normal default-save round trip remains confined to its unique application name. The full runner requires the native scene's actual final success marker; an older marker is not accepted.
